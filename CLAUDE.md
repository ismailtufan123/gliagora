## Session handoff

- The operator clears the session after each task and then says: "Pull main, then read docs/NEXT.md and do it." `docs/NEXT.md` holds that one task, written by the operator's planning chat; act on it only when the operator asks in the session.
- `docs/STATUS.md` is the one-page handoff: what is done, what is live, the open decisions and the next step, in plain language. Read it before `docs/NEXT.md`, and update it at the end of every task.
- When the task in `docs/NEXT.md` is finished, set its status to **done**, with the date and the pull request numbers, in the task's last pull request. The planning chat then replaces the file with the next task.

## Non-negotiable rules

### Privacy and law (PLAN §15, §18)

- All personal data stays on servers in Türkiye (D6, D22). Do not add any service that receives visitor or subscriber data: no Google Fonts, no external CDNs, no third-party analytics or tracking scripts, no embedded social widgets, no reCAPTCHA (spam protection is ALTCHA).
- Public pages load nothing from other domains. Fonts are self-hosted WOFF2.
- Local and staging environments use generated fake data only. Never put real personal data in fixtures, tests, logs, issues or prompts.
- Collect the minimum: the newsletter stores an email address only. No application-level IP logging; access-log retention follows PLAN §18.
- Social profiles (Instagram, LinkedIn) are plain `<a>` links (D14), hidden until the operator sends the exact addresses (D31); never guess them.

### Secrets

- Never commit secrets. Use a git-ignored `.env` and keep `.env.example` current with placeholder values (`deploy/.env.example` for the server). The app reads `DATABASE_URL`, `PAYLOAD_SECRET` (also the root of the keys in `src/lib/keys.ts`: the hashes of IP and email addresses for the form limits, the address code of unconfirmed data requests and the sealed sign-in cookie; changing it signs editors out, resets the limits, cancels sign-ins in progress and makes unconfirmed data requests unfindable), `ALTCHA_HMAC_KEY` (signs the spam-check challenges; without it the suggestion form says it is temporarily unavailable) and, for member sign-in (D49; each way stays off until its settings are set), `GOOGLE_CLIENT_ID`/`GOOGLE_CLIENT_SECRET` and `ORCID_CLIENT_ID`/`ORCID_CLIENT_SECRET`; not secrets, `EMAIL_CAP_HOUR`/`EMAIL_CAP_DAY` set the cap on the forms' emails (`src/lib/forms/email-cap.ts`, D50). The server's `.env` also holds listmonk's `LISTMONK_DB_PASSWORD` and `LISTMONK_API_TOKEN` (the app's API user; only its SHA-256 reaches listmonk), which `deploy/listmonk/prepare.sh` reads.
- Never print secrets in logs or CI output.

## How to work

- Small, reviewable steps: one branch from the latest `main` and one pull request per step. The PR description summarises what changed, how to run it and what to check.
- Proceed through approved milestone steps without waiting for review. Merge each step's PR yourself once `pnpm lint`, `pnpm typecheck`, `pnpm test` and the build pass (and CI is green), then continue from the updated `main`.
- CI minutes are limited (2,000 a month on GitHub Free, and CI and deploys stop when they run out; D46): a full CI run (a pull request that touches code) costs about 18–25 since M4b, a push to `main` on the fast path 4–8 (PLAN §11.5). Push a pull request's branch once its checks pass locally, since every push to it runs the whole CI again; put changes to `docs/STATUS.md` and the like into that same push, not a later one. A pull request whose whole diff touches only documentation (Markdown files and `docs/`, except `content/`, `docs/editor-guide-tr.md`, `docs/tr-strings-review.md` and `deploy/README.md`) runs no CI at all: merge it without waiting for a check (a task's documentation-only wrap-up pull request costs nothing). Merge a code pull request as soon as its run has passed and before any other: the push to `main` then has the tree its run tested and only builds, smoke-tests and pushes the image, while a `main` that moved in between (any other merge, documentation too) makes it run everything again (`.github/workflows/ci.yml`). If CI ever stops for lack of minutes, tell the operator at once.
- Before every merge, check that the latest CI run on `main` is green (`gh run list --branch main --workflow CI --limit 1`; without `--workflow CI` it may show a Deploy run). If it is red, fix `main` first; never merge on top of a red `main`.
- Stop and ask only before:
  - (a) anything that touches the production server (running commands on it or deploying to it);
  - (b) using real personal data;
  - (c) publishing legal texts (placeholders that say the texts are in preparation are fine).
- Explain any destructive command before running it.
- Test data logic (listing expiry, deduplication, taxonomy).
- Commit messages: short and imperative, e.g. "Add coming-soon page".
- If an implementation choice changes the plan, propose the `PLAN.md` edit in the same change.

## Code conventions

- User-visible text lives only in `messages/{locale}.json` (next-intl, PLAN §12). Lint rejects literal text in JSX: element text, conditionals and attributes people read or hear (`alt`, `title`, `aria-label`, `placeholder`, …). It cannot see text passed to your own components' props (e.g. `Lockup name=…`) or built in metadata, so take those from `t()` too. Both locales must have the same keys, placeholders and tags (a test checks this).
- Layouts hold text 40% longer than English (other languages, PLAN §12) and text at 200% on a 320px screen (WCAG 1.4.4): buttons wrap a label that does not fit, long words break, and nothing relies on a text's width. `tests/e2e/pseudo-locale.spec.ts` checks the main templates in a pseudo-locale and `tests/e2e/layout.spec.ts` every template in `pages.ts`; add new templates or states (menus, sheets, errors) there, and those of the M2 state's reduced header and footer (its pages, its phone menu) to `tests/e2e/m2.spec.ts`, the only project that sees them. Text that is the same in every language (the brand lockup) carries `translate="no"`, which the pseudo-locale leaves alone. The header's lockup gives way when the header needs room (a container query in `global.css`); keep its widths in step with `Lockup.tsx`.
- Colours, type sizes, radii and shadows come only from the design tokens (`src/app/(frontend)/tokens.css`, exposed as Tailwind utilities). A test rejects raw colour values anywhere else; the only exception is the browser theme colour in `src/lib/metadata.ts`, which the test checks against the `--bg` tokens.
- Each locale is a static folder: `src/app/(frontend)/en/…` and `src/app/(frontend)/tr/…`. URLs always end with a slash. Pages that exist only in English link there from other locales (`paths` in `src/lib/site.ts`).
- Long-form pages (About, legal texts) are Markdown in `content/{locale}/…`, listed in `src/lib/content.ts` and rendered by `ContentPage` (D28). A legal text keeps `draft: true` (draft notice, `noindex`) until the operator approves that exact text; never set it to `false` on your own, and do not merge a change to an approved (non-draft) legal text without the operator's approval. In these files, mark a phrase in another language as `{en: Suggest a listing}` or `{tr: açık rıza}` (WCAG 3.1.2), and an open point as `[TO DECIDE: …]` / `[KARAR VERİLECEK: …]`; links may only be site paths, `https://`, `http://` or `mailto:`, and this site's own pages only by their paths (`/en/about/`, never `https://gliagora.com/…`). `docs/m2-links-review.md` shows how each text's links read in the M2 state (`pnpm m2:links`).
- Public forms follow "Suggest a listing" (`src/lib/forms/`, `src/components/suggest/`): a Server Action with `useActionState`, so every check and message comes from the server and the form works without JavaScript except for the spam check; zod on the server; ALTCHA with our own small solver (never the widget, never `setCookie`); a honeypot that answers as if it worked; a rate limit on the HMAC of the client IP in the hidden `form-limits` collection (never the raw IP, never in logs); an error summary that takes focus. Log failures with a reference and the error's class only, never what was sent.
- Navigation lives in `src/lib/site.ts` (windows, sections, paths) and `src/lib/navigation.ts` (mega-menus). Every link in the header and footer must lead to a page (an end-to-end test checks this): a section that is not built yet gets a `PlaceholderPage` (`noindex`) until its milestone.
- Public forms ("Suggest a listing", "Report a problem") share their server checks (zod fields, hidden field, ALTCHA, a rate limit per form, messages) in `src/lib/forms/public-form.ts` and their browser parts (spam check, error summary, fields) in `src/components/forms/`; a new form reuses them, with its own rate-limit bucket in `src/lib/forms/rate-limit.ts`.
- Header menus are `<details>` disclosures that work without JavaScript; `DisclosureEnhancer` adds Esc, outside click and the mobile menu's inert background. It serves disclosures in pages too: a `data-modal` disclosure outside the header (the jobs filter sheet) becomes a modal dialog over an inert page, with a `[data-disclosure-close]` button (one opened before JavaScript ran stays in the page, `data-inline`, until it is closed). It sets `<html data-js>`; `.js-only` elements show only then.
- Icons come from `src/components/Icon.tsx`: Lucide's shapes drawn on the server as plain SVG, so no icon code reaches the browser (D45). Add a shape there when a new icon is needed.
- Filtered lists use the shared filter model in `src/lib/filters/` (PLAN §2.4): read a list's query with its `parse…` function and build every link to a list with its helpers (e.g. `jobsHref({ type: ['phd'] })`), never by hand, so links are canonical; the proxy redirects any other spelling (keeping `utm_*` tags). Parameters that depend on each other are brought in line by the list's `normalise` (the jobs list keeps `prefs=off` only without filters). A signed-in member's preferred subfields apply only to the bare jobs list (D35, `src/lib/jobs/preferred.ts`): the page queries and shows `effective` and builds its links from `links`, which say `prefs=off` for such a member wherever they lead back to the bare list. The jobs list's browser behaviour (`ListBehaviour`) loads only when the reader first reaches for the filters, chips or sort order (`JobsListEnhancer` keeps what they do until it arrives, D45); keep it there rather than in the page's first script. Public pages have no `loading.tsx`: Next.js streams it first, and without JavaScript the real content never replaces it.
- The home page (`src/app/(frontend)/en/page.tsx`, `src/components/home/`, M6) reads its figures and lists through `src/lib/home.ts`; each figure equals the number its link's list shows to a signed-out visitor (`tests/e2e/home.spec.ts`; for a member with preferred subfields the jobs list applies the default to the bare list, D35, while its head line still equals the "open positions" figure): the positions and deadlines come from the jobs list's own filter code (`countOpenJobs` in `src/lib/records.ts`), the institutions and countries from `openJobsCoverage`. The figures are kept for 10 minutes (and read again when the month changes); the two short lists are read with each request. The institutions figure counts the institutions the map pins, as its link leads there. A window's label appears around the poster once the window is listed in `LIVE_WINDOWS` (`src/lib/site.ts`); its card in the windows overview (`HomeWindows.tsx`) is added in the milestone that builds it. The hero's poster is generated by `tools/poster`; regenerate it rather than edit `HomePoster.tsx` by hand.
- Search SQL lives only in `src/lib/search/`: Drizzle's `sql` tag through Payload's own connection, every value (above all what people type) a parameter, never string concatenation. Folding (case, Turkish İ/ı, accents) happens in PostgreSQL with `public.f_unaccent(lower(…))`, never in JavaScript. The queries repeat the expressions of the search indexes (migration `20260928_100000_search`) exactly, or the indexes go unused; `pnpm test:db` checks the plans. Payload does not know those indexes and `pnpm migrate:create` leaves them alone; a raw-SQL migration keeps its own `down`.
- Do not call `notFound()` inside a page: in Next.js 16.3 its 404 content renders only with JavaScript. Unknown public URLs, including unknown paths under `/en/` and `/tr/`, already get the server-rendered global 404 (`src/app/global-not-found.tsx`); `/admin` and `/api` answer their own 404s (Payload). Removed fixed paths answer 410: `src/proxy.ts` checks `isGone()` in `src/lib/gone.ts` and shows the removed-page with status 410. Pages that show a database record (institutions, subfield hubs, jobs; events from M8) are resolved in the proxy before rendering (`src/lib/detail-routes.ts`, with the database lookup in `src/lib/detail-lookup.ts`): unknown record, draft or job in review → 404, outdated or missing slug → 308, retired subfield, withdrawn job, job closed 30 days ago or job retired 12 months after that (only its address and ID kept in `retired-listings`, D34) → 410 with the same removed-page (`listingState()` in `src/lib/jobs/deadline.ts`). Add each new detail route there, and give its page `export const dynamic = 'force-dynamic'` (the build has no database).
- The M2 state (D41, D50) is one setting, `SITE_STAGE` (`private` by default, or `m2`), which Caddy and the app both read (`src/lib/site-stage.ts`, at request time). Its public pages are one list, `src/lib/public-pages.ts` (a legal text only once `draft: false`); each page there has an M2 version, its twin under `src/app/(frontend)/m2/{en,tr}/…` (root layouts with the reduced header and footer, `stage="m2"`), which the proxy shows in its place in the M2 state (a rewrite for every method, keeping the query; `/m2/…` itself answers 404). A twin re-exports an unchanged page (`export { default, generateMetadata } from …`, with `dynamic` written in its own file) or passes `stage="m2"` where the page differs (`ContentPage`, whose links then lead only to public pages or to email, `src/lib/m2-links.ts`). A component that reads the path (`usePathname()`) takes it through `publicPathname()`, or the twin's `/m2/…` path makes React render the page again. A new public page: one line in the list, its twin (a unit test checks both ways), then `pnpm caddy:public`; the M2 state's tests are `tests/e2e/m2.spec.ts`. Caddy opens each address only in its exact spelling (a regexp on the raw address), answers the app's 404s and 410s with a plain "Not Found", and Caddy and the app mark each other's public requests and answers (`PUBLIC_MARK`, `X-Gliagora-Public`): the proxy refuses a marked request its image does not hold public, and Caddy passes only marked answers to pages, machine files and forms, so a copy of the list on the server that is ahead of the running image opens nothing more. Nothing in the full site changes while the stage is `private`.
- Robots rules live in `src/lib/indexing.ts`: a page's robots metadata and its sitemap entry (`src/lib/seo/sitemap-entries.ts`) come from the same function, so a page is in the sitemaps exactly when it is indexed. A new indexable page or record type gets its entry there too; `tests/e2e/seo.spec.ts` checks that every listed URL answers 200, without `noindex`, and names itself as canonical. The machine files (`/sitemap.xml`, `/sitemaps/*.xml`, `/en/jobs/feed.xml`) are route handlers that read the database at request time and answer 503 while it is unreachable; a name under `/sitemaps/` that no sitemap file can have gets the global 404 from the proxy.
- Access (PLAN §18.2): signed out, Payload's API gives nothing; public pages read through the local API with their own queries. Every collection and global states its rule for each operation with `signedIn` or `nobody` from `src/lib/access.ts`; a rule written as a function replaces Payload's default user check, so it checks `req.user` itself (field rules too). `tests/e2e/access.spec.ts` enumerates every collection and global from `src/payload-types.ts` and sends signed-out requests for every operation: a new collection needs an entry in its table, and a deliberately public read needs a reason there and a comment where its rule is set (`src/lib/access.test.ts` checks the rules as written). GraphQL is off.
- The Turkish editor guide, `docs/editor-guide-tr.md`, is what the admin shows at `/admin/help/` ("Yardım" at the end of the side menu, `src/admin/help.ts`, D45): keep it in step with the admin when the admin changes. It is read at run time, so it is kept in the Docker image (`.dockerignore`) and in the server build (`outputFileTracingIncludes` in `next.config.ts`).
- Payload is loaded from `node_modules`, not bundled (`serverExternalPackages` in `next.config.ts`): bundled, the production build copies it into each part of the server (instrumentation, proxy, routes, pages), and errors thrown by one copy fail `instanceof` in another, so the admin loses the per-field messages of refused saves. Keep it that way; `tests/e2e/admin-api.spec.ts` checks it.
- The map (PLAN §14, `src/components/map/`) loads MapLibre GL JS natively from `/map/maplibre-gl/<version>/`, which `src/scripts/vendor-maplibre.mjs` copies from `node_modules` before `next build` and `next dev`; never bundle it: its worker then comes from our origin (the CSP allows no `blob:` workers) and shares MapLibre's code with the page. Map code loads only where a map is shown (`engine.ts` on demand; on the jobs list through `LazyMapView`, since the list has about 0.26 KB of its 137 KB cap left: 136.74 KB, PLAN §17.3), within the map budget of `tests/e2e/budgets.spec.ts` (§17.3). The basemap's files are named by `/basemap/current.json` (`deploy/basemap/fetch-basemap.sh`; the tests serve `tests/fixtures/basemap` with `serveBasemap`, and check the map under the CSP of `deploy/Caddyfile` with `withSiteCsp`, `tests/e2e/map.ts`). Map colours come from the tokens at runtime. The map's data (`/api/map/institutions/`) resolves the jobs list's filters with the list's own code (`resolveJobFilters` in `src/lib/records.ts`), so map and list always count the same positions.
- listmonk (M2, D50; `deploy/README.md` section 11) is set up only from `deploy/`: its database by `deploy/postgres/init/20-listmonk-database.sh`, its install and settings by `deploy/listmonk/prepare.sh` (on every `update.sh`), the settings, the list Glia Notes and the app's API user by `deploy/listmonk/settings.sql`, plain SQL that the server applies with psql and `pnpm listmonk:setup`, the tests (`tests/integration/listmonk.ts`, `startListmonk()`) and CI with node-postgres; change a listmonk setting there, never only in its admin. Its admin is reached only through an SSH tunnel (no route in Caddy, no subdomain); its image is pinned once in `compose.yaml` and once in `deploy/compose.prod.yml` (a test checks they agree). listmonk treats role 1 as its super admin, so the file refuses a listmonk installed without its admin. The app's API user may only get, add, change and delete subscribers of Glia Notes; it finds one by ID (`GET /api/subscribers/:id`, then compare the UUID) or by address (`?search=`), never by `?query=`: never give it `subscribers:sql_query`, whose expressions listmonk checks only by the tables in their plan (`query_to_xml` and `ts_stat` read any table, its admin sessions and SMTP password included; `tests/integration/listmonk.db.test.ts` checks the refusal). Local listmonk (`compose.yaml`) connects as its own role, never as the superuser. Nothing depends on listmonk: when `prepare.sh` fails, `update.sh` starts everything else and exits 3, and `deploy-remote.sh` keeps the healthy app. The scripts that read `/opt/gliagora/.env` themselves (`prepare.sh`, `alert.sh`) use the shared `env_value`, which refuses a line Compose would read differently (`$`, `\`, `"`, `#` outside single quotes): values with such characters go in single quotes. Every container in `deploy/compose.prod.yml` logs to the systemd journal (14 days, D34); backup and restore-test results are emailed by `deploy/backup/alert.sh` once `SMTP_HOST` and `ALERT_EMAIL` are set. `src/lib/deploy-scripts.test.ts` runs the deploy scripts against stand-ins (`tests/fixtures/deploy/bin`): add to it when a script changes.
- Scheduled work lives in `src/jobs/`: the maintenance tasks (`src/jobs/maintenance/`, registered in `payload.config.ts` in the `maintenance` queue) are built with `maintenanceTask()`: idempotent, in bounded batches, one run at a time (a PostgreSQL lock), and logs and stored job errors with counts, IDs and error classes only (`src/lib/errors.ts`), never personal data. They run only where `PAYLOAD_JOBS_AUTORUN` is `true` (production). Retention periods are in `src/lib/retention/rules.ts` (D34). Code that deletes or clears personal data also clears the collection's saved versions (e.g. `_candidates_v`), since Payload keeps a copy of every save and has no route to delete one; deleting a record through the local API removes its versions. Automatic emails go through `deliver()` (or `sendOne()`, which also reports the SMTP reply code and enhanced status, never the reply's text; `src/lib/email/deliver.ts`, re-exported by `src/jobs/maintenance/email.ts`) only when `canSendEmail()` is true (SMTP_HOST set), are plain text from the `emails` messages, and set their sent-time only after the mail server accepted the message.
- Member accounts (M4b, D49, PLAN §18.2) are never Payload auth: `users` stays the only collection with `auth`, and the member collections (`members`, `member-sessions`, `email-tokens`, `saved-items`) and `deletion-log` are hidden, `nobody` for every operation and without API routes (`HIDDEN_RECORDS` in `src/collections/hidden.ts`; `src/lib/access.test.ts` checks both); editors see only `data-requests`. Member rows are read and written in `src/lib/members/store.ts` only: Drizzle's `sql` with every value a parameter, through Payload's connection, several tables in one transaction. That skips Payload's hooks and field checks, so the limits are zod checks there and the rules that matter are database constraints (the raw-SQL migration `20261001_142246_member_constraints`, with its own `down`): change both together. Store functions throw `MemberStoreError` (a code and a constraint name, never values). Tokens (sessions, email links) are 32 random bytes and only their SHA-256 is stored; a link is only looked up on GET and is consumed by a POST, for its own purpose, in one `DELETE … RETURNING`. Member POST routes check `sameOrigin()` and answer `303` with a relative `Location` (`seeOther()` in `src/lib/members/responses.ts`; an outcome as `?done=`/`?error=` with `#outcome`, allow-listed in `src/lib/members/outcome.ts`); the site's origin is `appOrigin()` (`src/lib/members/origin.ts`), never `request.url`; `next` goes through `safeNext()` and `save` through `parseSave()`. Only dynamic pages read who is signed in, through `currentMember()` (`src/lib/members/session.ts`: once per request, and only when the request has a session cookie); the header is the same for everyone (one Account link), so static pages stay static. Member pages are English only under `/en/sign-in/`, `/en/sign-out/` and `/en/account/` (`MEMBER_PATHS`), never indexed (`memberPageIndexed()`), disallowed in robots.txt, and their query strings are removed from both of Caddy's logs. Public-form Server Actions refuse calls Next.js forwarded from another page (`handlePublicForm`), and a form that sends an email adds `emailLimits()` to its own. Google and ORCID sign-in is OpenID Connect through `oauth4webapi` in `src/lib/members/oidc.ts` (state and nonce always, PKCE where the provider's discovery advertises S256, the client secret in the body, the ID token's signature checked); its routes are links (GET) in `src/lib/members/provider-routes.ts`, a new identity makes an account only through "Create account" (`/en/sign-in/confirm/`), and `resolve()` (`src/lib/members/identity.ts`) decides every sign-in, link and removal, applied by `src/lib/members/provider-sign-in.ts`; every change of sign-in methods ends the member's other sessions. Save buttons are `SaveControl` (`src/components/account/SaveControl.tsx`): a page reads `saveContext()` once for its rows (nothing while no sign-in method is on, a sign-in link signed out, a form signed in) and passes it as `save` to `JobList`, whose rows then get the ID `job-{shortId}` (only then, so no ID repeats); every form posts to one route (`/en/account/saved/toggle/`, rules in `src/lib/members/saved.ts`), and the script that takes it over loads on first use (`save-toggle.ts`, a few lines in `DisclosureEnhancer`). The account's settings (Glia Notes, preferred subfields, display name, removing a method) are plain forms posting to `/en/account/settings/` with an `intent` (rules in `src/lib/members/settings.ts`); the Glia Notes choice is only stored until M2 (listmonk). Adding or changing the address is the one ALTCHA form there (`sendVerifyLink`, `src/lib/forms/verify-email.ts`): a `verify-email` link bound to the member who asked, used on `/en/sign-in/link/` only by that member, signed in (`src/lib/members/verify-email.ts`). The privacy page (`/en/account/privacy/`) holds "Download my data" (a GET of `…/export/`, `src/lib/members/export.ts`: a JSON attachment, schema `gliagora-export/1`, never a token), "Sign out everywhere" and "Delete my account", a link to its own confirmation page (`…/delete/`, never a dialog), whose button posts to `…/delete/use/` (`src/lib/members/account-deletion.ts`): one transaction records a closed `deletion` data request (source `account`), calls `eraseNewsletter()` (`src/lib/newsletter/erase.ts`, a no-op until M2) and `deleteMember()`. The data-request form (`/en/legal/data-requests/#request-form`, `sendDataRequest` through `handlePublicForm`, `src/lib/forms/data-request.ts`) records each request at once with only its kind, date and keyed address hash (`src/lib/data-requests/record.ts`; the database refuses more while it is `unconfirmed`) and keeps what the person wrote in a `data-request` link (24 h); the link's page (`…/confirm/`) only reads, and its button posts to `…/confirm/use/` (`src/lib/data-requests/confirm.ts`), which in one transaction consumes the link and either deletes by address (suggestions by `lower(email)` through the local API, `deleteMember()`, report addresses cleared and logged as `clear-email` except personal-rights reports) and closes the record, or records the request as New for an editor. The data-request record is the outbox of the final email (`sendRequestEmails`); the member tasks (`cleanInactiveMembers`, `purgeMemberAuth`, `applyDeletionLog`) go through the store's functions too, and their rules are in `src/lib/retention/rules.ts`. Tests use the fake providers in `tests/fake-oidc/server.ts` (a fixed, public test key, trusted only through `AUTH_TEST_ISSUER`). Nothing about members is logged but references, outcomes and error classes: no tokens, addresses, provider IDs, names, `next`, cookie values or SMTP reply texts. A deletion of personal data that a person asked for, or that the inactivity rule made, writes a `deletion-log` row in its own transaction (the `logDeletions()` hooks of suggestions and reports, `deleteMember()` for members, the only way to delete one), so it is repeated after a restore, but only on a record created no later than the logged deletion (a restore sets the ID sequences back, so a newer record can have a logged ID); the retention task's deletions are not logged (they repeat themselves), and neither is removing fake data.
- Calendar days (a job's deadline day, "Last verified") are Payload date fields stored at noon UTC, so their UTC date is the day in every time zone; read them with `calendarDay()` and get instants with `deadlineEnd()` in `src/lib/jobs/deadline.ts` (a deadline day ends at midnight in `deadlineTz`, the institution's time zone unless the posting names another, or Anywhere on Earth when the zone is unknown; the institution's time zone is `Institution.timeZone`, from its coordinates, checked against its country (`timeZoneAt()` in `src/lib/jobs/time-zone-at.ts`, server-side only), which a new job takes when it is created without one, D40), never with the server's or the browser's time zone. Show them with `formatDay()` and `deadlineView()` in `src/lib/jobs/format.ts`, and take "now" from `requestTime()` in `src/lib/records.ts`, read once per request so a page, its lists and its metadata agree.

## Commands

Fill these in as the project grows.

- `docker compose up -d db` — start local PostgreSQL (values from `.env`; copy `.env.example`)
- `pnpm migrate` — apply database migrations
- `pnpm dev` — run the app locally (site on `/`, admin on `/admin`)
- `pnpm lint`, `pnpm typecheck`, `pnpm test` — checks (`pnpm format` fixes formatting)
- `pnpm test:db` — tests against PostgreSQL (`*.db.test.ts`), which need a connection that may create databases (`TEST_DATABASE_URL`, locally the `DATABASE_URL` of `.env`): those under `src/` each make and drop their own scratch database and role; those under `tests/integration/` (the scheduled tasks) share one scratch database, created, migrated and dropped again, and a throwaway Mailpit for the email tests (a container where Docker is available, else the Mailpit program named by `MAILPIT_BIN`; skipped without either); CI runs them too
- `pnpm test:e2e` — Playwright + axe tests against a running app (`pnpm build && pnpm start`, with the ROR test data and `pnpm fake:jobs` loaded; start the app after loading them, since it keeps the home page's figures for 10 minutes); every new page template goes into `tests/e2e/pages.ts` (`member: 'email' | 'orcid' | 'saver'` signs it in as a test member). Playwright reads `.env` too (the environment wins). The member tests need `pnpm e2e:member` and `E2E_MEMBER_TOKEN`, and the sign-in flows an app that sends to Mailpit (`SMTP_HOST=127.0.0.1`, `SMTP_PORT=1025`) with `MAILPIT_URL` (e.g. `http://127.0.0.1:8025`); without them they are skipped locally (CI always has them). `BASE_URL` sets the app's address (default `http://localhost:3000`) and `PLAYWRIGHT_CHROMIUM_EXECUTABLE` a Chromium already installed; the project `m2` (`tests/e2e/m2.spec.ts`, skipped locally without them) needs `CADDY_BIN` (Caddy 2.11.4, the production image's version) and `M2_APP_URL` (a second `pnpm start` with `SITE_STAGE=m2` and its own `PORT`), and then starts the production Caddyfile in front of both apps itself (`tests/caddy/serve.ts`, HTTPS ports `CADDY_M2_PORT`, `CADDY_PRIVATE_PORT` and `CADDY_WIDE_PORT`, 8443, 8444 and 8445 by default, each with its plain-HTTP port 100 above; the M2 app must be running whenever `M2_APP_URL` is set); with `--reporter=html` the report holds the pseudo-locale screenshots, and `budgets.spec.ts` prints each template's sizes
- `pnpm migrate:create <name>`, then `pnpm generate:types` — after changing a collection; commit the migration and types with it
- `pnpm migrate:status` — list the migrations and whether each has run
- `pnpm generate:importmap` — after adding or moving a custom admin component (such as the review dashboard); commit `src/app/(payload)/admin/importMap.js` with it
- `pnpm ror:import tests/fixtures/ror/v2.13-2026-09-22-ror-data-sample.zip` — load 20 test institutions (21 ROR records, one withdrawn and skipped; the e2e tests need them); without a file it downloads and imports the latest ROR release (about 15 minutes the first time)
- `pnpm fake:jobs` — replace the fake jobs at the test institutions (run it after `pnpm ror:import`): about 60 generated ones plus the fixed ones the e2e tests use (`src/scripts/fake-jobs-fixed.ts`: open, closing soon, rolling, closed recently, gone, withdrawn, draft (at an institution added by hand, the one an editor could delete), and a retired listing), then fake review-queue suggestions, candidates, reports and data requests in every state (`src/scripts/fake-queue-data.ts`; it also removes those the e2e tests sent). It refuses to run where `PAYLOAD_JOBS_AUTORUN` is `true` (production)
- `pnpm jobs:run [task …]` — run the scheduled maintenance tasks once (the hourly expiry, the form-limit and retention purges, the job places, the automatic emails, and the member tasks: inactivity warnings and deletions, expired sessions and links, the deletion log after a restore, the email after a deletion of an account or of data from the data-request form; `src/jobs/maintenance/`), all of them or those named; the same tasks the production server runs on its schedule
- `pnpm caddy:public` — rewrite `deploy/caddy/m2-public.caddy`, the addresses Caddy opens in the M2 state, after a change to `src/lib/public-pages.ts`, to a legal text's `draft` flag or to the files in `public/brand/` (a unit test fails until then)
- `pnpm m2:links` — rewrite `docs/m2-links-review.md`, every link of the texts in `content/` that the M2 state turns into an email or its words alone, with its sentence, for the operator to read before approving a text; after a change to a text or to `src/lib/m2-links.ts` (a unit test fails until then)
- `pnpm tr:review` — regenerate `docs/tr-strings-review.md`, the table of every Turkish interface string for the native speaker's review (D40), after changing `messages/*.json`; a unit test fails when the file is out of date or a new key has no "where it appears" in `src/scripts/tr-strings-review-areas.ts`
- `docker compose --profile newsletter up -d listmonk` — local listmonk (M2) at http://127.0.0.1:9000/admin/, in a database `listmonk` of the local PostgreSQL, connected as its own role `listmonk` (`LISTMONK_DB_PASSWORD` from `.env`) (user gliagora-admin with `LISTMONK_ADMIN_PASSWORD` from `.env`, at least 8 characters, before its first start); then `LISTMONK_DATABASE_URL=… LISTMONK_API_TOKEN=… pnpm listmonk:setup` applies the server's settings (`deploy/listmonk/settings.sql`) and `docker compose restart listmonk` makes it read them. Without Docker, `LISTMONK_BIN` (the release's linux binary) lets `pnpm listmonk:setup` install it and `pnpm test:db` start it (`tests/integration/listmonk.db.test.ts`; skipped without Docker or `LISTMONK_BIN`)
- `docker compose --profile mail up -d mailpit` — local mail server for testing emails: set `SMTP_HOST=127.0.0.1` and `SMTP_PORT=1025` in `.env` (see `.env.example`) and read the messages at http://127.0.0.1:8025; nothing leaves the computer. Stop it with `docker compose --profile mail rm --stop --force mailpit`
- `E2E_EDITOR_PASSWORD=… pnpm e2e:editor` — add (or reset) the test editor `e2e-editor@example.org` that the admin API and access end-to-end tests use (one sign-in per run, `tests/e2e/editor.ts`: parallel sign-ins as one user drop each other's session); pass the same `E2E_EDITOR_PASSWORD` to `pnpm test:e2e` (without it the admin API test is skipped locally and the access test uses small IDs; CI always has it). It refuses to run where `PAYLOAD_JOBS_AUTORUN` is `true` (production)
- `pnpm fake:oidc` — the fake Google and ORCID of the tests (`tests/fake-oidc/server.ts`, test only) where `AUTH_TEST_ISSUER` says (default `http://127.0.0.1:9400`); give the app the same `AUTH_TEST_ISSUER` and it uses them instead of the real providers (honoured only on this computer, never where `PAYLOAD_JOBS_AUTORUN` is `true`). `pnpm test:e2e` starts them itself when `AUTH_TEST_ISSUER` is set; without it the Google and ORCID tests are skipped locally (CI always has it)
- `E2E_MEMBER_TOKEN=… pnpm e2e:member` — add the test members (`e2e-member@example.org`, an ORCID-only member and `e2e-saver@example.org`, whose saved positions a test removes; `src/scripts/e2e-member-account.ts`), each with one session whose cookie the tests make from the same `E2E_MEMBER_TOKEN` (pass it to `pnpm test:e2e`); the two with an address have saved three fixed fake jobs (open, closed recently, withdrawn), and `e2e-member@example.org` prefers two subfields (D35), so run it after `pnpm fake:jobs`, and again before each `pnpm test:e2e` (new sessions, the saved positions, the preferred subfields and the form limits reset). It refuses to run where `PAYLOAD_JOBS_AUTORUN` is `true` (production)
- `gh workflow run deploy.yml --ref main -f tag=sha-1234567` (or GitHub → Actions → Deploy) — deploy by hand, only when the operator asks (a rollback, say): `main` or `sha-` plus 7 characters of a commit; merges to `main` deploy by themselves until M2, release tags `v…` from M2 on (D43); a new image that does not become healthy is rolled back by itself (`deploy/README.md`, "How deploys work")
- `sudo /opt/gliagora/basemap/fetch-basemap.sh [YYYYMMDD | --rollback]` (on the server, only when the operator asks) — the map's basemap, about twice a year (`deploy/README.md` step 8); `tools/basemap/make-fixture.sh` rebuilds the tests' small basemap
