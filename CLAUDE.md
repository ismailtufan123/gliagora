## Stack (PLAN §11)

- One TypeScript app: Next.js (App Router) + Payload CMS 3, on PostgreSQL. Package manager: pnpm. Node.js: current LTS.
- Docker Compose for local development and production. Images are built in GitHub Actions and pushed to GHCR; the server only pulls and runs them (it has 4 GB RAM, so it never builds).
- Production services on one server: Caddy (TLS and reverse proxy), the app, one PostgreSQL instance (separate databases for Payload, listmonk and Umami), listmonk (newsletter), Umami (cookieless analytics).
- Later milestones: MapLibre with self-hosted PMTiles (M5); Three.js + GSAP hero on the home route only (M13).

## Non-negotiable rules

### Privacy and law (PLAN §15, §18)

- All personal data stays on servers in Türkiye (D6, D22). Do not add any service that receives visitor or subscriber data: no Google Fonts, no external CDNs, no third-party analytics or tracking scripts, no embedded social widgets, no reCAPTCHA (spam protection is ALTCHA).
- Public pages load nothing from other domains. Fonts are self-hosted WOFF2.
- Local and staging environments use generated fake data only. Never put real personal data in fixtures, tests, logs, issues or prompts.
- Collect the minimum: the newsletter stores an email address only. No application-level IP logging; access-log retention follows PLAN §18.
- Social profiles (Instagram, LinkedIn) are plain `<a>` links (D14), hidden until the operator sends the exact addresses (D31); never guess them.

### Secrets

- Never commit secrets. Use a git-ignored `.env` and keep `.env.example` current with placeholder values (`deploy/.env.example` for the server). The app reads `DATABASE_URL`, `PAYLOAD_SECRET` (also the source of the key that hashes IP addresses for form rate limits) and `ALTCHA_HMAC_KEY` (signs the spam-check challenges; without it the suggestion form says it is temporarily unavailable).
- Never print secrets in logs or CI output.

### Content

- Job listings link to the employer's own page (PLAN §15).
- Papers of the month: openly licensed only (CC BY, CC BY-SA, CC0) (D4).
- Bench to Bedside: research translation only, never medical advice (D19).

## How to work

- Small, reviewable steps: one branch from the latest `main` and one pull request per step. The PR description summarises what changed, how to run it and what to check.
- Proceed through approved milestone steps without waiting for review. Merge each step's PR yourself once `pnpm lint`, `pnpm typecheck`, `pnpm test` and the build pass (and CI is green), then continue from the updated `main`.
- Before every merge, check that the latest CI run on `main` is green (`gh run list --branch main --workflow CI --limit 1`; without `--workflow CI` it may show a Deploy run). If it is red, fix `main` first; never merge on top of a red `main`.
- Stop and ask only before:
  - (a) anything that touches the production server (running commands on it or deploying to it);
  - (b) using real personal data;
  - (c) publishing legal texts (placeholders that say the texts are in preparation are fine).
- Explain any destructive command before running it.
- Test data logic (listing expiry, deduplication, taxonomy).
- Commit messages: short and imperative, e.g. "Add coming-soon page".
- If an implementation choice changes the plan, propose the `PLAN.md` edit in the same change.

## Code conventions

- User-visible text lives only in `messages/{locale}.json` (next-intl, PLAN §12). Lint rejects literal text in JSX: element text, conditionals and attributes people read or hear (`alt`, `title`, `aria-label`, `placeholder`, …). It cannot see text passed to your own components' props (e.g. `Lockup name=…`) or built in metadata, so take those from `t()` too. Both locales must have the same keys, placeholders and tags (a test checks this).
- Layouts hold text 40% longer than English (other languages, PLAN §12) and text at 200% on a 320px screen (WCAG 1.4.4): buttons wrap a label that does not fit, long words break, and nothing relies on a text's width. `tests/e2e/pseudo-locale.spec.ts` checks the main templates in a pseudo-locale and `tests/e2e/layout.spec.ts` every template in `pages.ts`; add new templates or states (menus, sheets, errors) there. Text that is the same in every language (the brand lockup) carries `translate="no"`, which the pseudo-locale leaves alone. The header's lockup gives way when the header needs room (a container query in `global.css`); keep its widths in step with `Lockup.tsx`.
- Colours, type sizes, radii and shadows come only from the design tokens (`src/app/(frontend)/tokens.css`, exposed as Tailwind utilities). A test rejects raw colour values anywhere else; the only exception is the browser theme colour in `src/lib/metadata.ts`, which the test checks against the `--bg` tokens.
- Each locale is a static folder: `src/app/(frontend)/en/…` and `src/app/(frontend)/tr/…`. URLs always end with a slash. Pages that exist only in English link there from other locales (`paths` in `src/lib/site.ts`).
- Long-form pages (About, legal texts) are Markdown in `content/{locale}/…`, listed in `src/lib/content.ts` and rendered by `ContentPage` (D28). A legal text keeps `draft: true` (draft notice, `noindex`) until the operator approves that exact text; never set it to `false` on your own, and do not merge a change to an approved (non-draft) legal text without the operator's approval. In these files, mark a phrase in another language as `{en: Suggest a listing}` or `{tr: açık rıza}` (WCAG 3.1.2), and an open point as `[TO DECIDE: …]` / `[KARAR VERİLECEK: …]`; links may only be site paths, `https://`, `http://` or `mailto:`.
- Public forms follow "Suggest a listing" (`src/lib/forms/`, `src/components/suggest/`): a Server Action with `useActionState`, so every check and message comes from the server and the form works without JavaScript except for the spam check; zod on the server; ALTCHA with our own small solver (never the widget, never `setCookie`); a honeypot that answers as if it worked; a rate limit on the HMAC of the client IP in the hidden `form-limits` collection (never the raw IP, never in logs); an error summary that takes focus. Log failures with a reference and the error's class only, never what was sent.
- Navigation lives in `src/lib/site.ts` (windows, sections, paths) and `src/lib/navigation.ts` (mega-menus). Every link in the header and footer must lead to a page (an end-to-end test checks this): a section that is not built yet gets a `PlaceholderPage` (`noindex`) until its milestone.
- Public forms ("Suggest a listing", "Report a problem") share their server checks (zod fields, hidden field, ALTCHA, a rate limit per form, messages) in `src/lib/forms/public-form.ts` and their browser parts (spam check, error summary, fields) in `src/components/forms/`; a new form reuses them, with its own rate-limit bucket in `src/lib/forms/rate-limit.ts`.
- Header menus are `<details>` disclosures that work without JavaScript; `DisclosureEnhancer` adds Esc, outside click and the mobile menu's inert background. It serves disclosures in pages too: a `data-modal` disclosure outside the header (the jobs filter sheet) becomes a modal dialog over an inert page, with a `[data-disclosure-close]` button (one opened before JavaScript ran stays in the page, `data-inline`, until it is closed). It sets `<html data-js>`; `.js-only` elements show only then.
- Icons come from `src/components/Icon.tsx`: Lucide's shapes drawn on the server as plain SVG, so no icon code reaches the browser (D45). Add a shape there when a new icon is needed.
- Filtered lists use the shared filter model in `src/lib/filters/` (PLAN §2.4): read a list's query with its `parse…` function and build every link to a list with its helpers (e.g. `jobsHref({ type: ['phd'] })`), never by hand, so links are canonical; the proxy redirects any other spelling (keeping `utm_*` tags). The jobs list's browser behaviour (`ListBehaviour`) loads only when the reader first reaches for the filters, chips or sort order (`JobsListEnhancer` keeps what they do until it arrives, D45); keep it there rather than in the page's first script. Public pages have no `loading.tsx`: Next.js streams it first, and without JavaScript the real content never replaces it.
- The home page (`src/app/(frontend)/en/page.tsx`, `src/components/home/`, M6) reads its figures and lists through `src/lib/home.ts`; each figure equals the number its link's list shows (`tests/e2e/home.spec.ts`): the positions and deadlines come from the jobs list's own filter code (`countOpenJobs` in `src/lib/records.ts`), the institutions and countries from `openJobsCoverage`. The figures are kept for 10 minutes (and read again when the month changes); the two short lists are read with each request. The institutions figure counts the institutions the map pins, as its link leads there. A window's label appears around the poster once the window is listed in `LIVE_WINDOWS` (`src/lib/site.ts`); its card in the windows overview (`HomeWindows.tsx`) is added in the milestone that builds it. The hero's poster is generated by `tools/poster`; regenerate it rather than edit `HomePoster.tsx` by hand.
- Search SQL lives only in `src/lib/search/`: Drizzle's `sql` tag through Payload's own connection, every value (above all what people type) a parameter, never string concatenation. Folding (case, Turkish İ/ı, accents) happens in PostgreSQL with `public.f_unaccent(lower(…))`, never in JavaScript. The queries repeat the expressions of the search indexes (migration `20260928_100000_search`) exactly, or the indexes go unused; `pnpm test:db` checks the plans. Payload does not know those indexes and `pnpm migrate:create` leaves them alone; a raw-SQL migration keeps its own `down`.
- Do not call `notFound()` inside a page: in Next.js 16.3 its 404 content renders only with JavaScript. Unknown public URLs, including unknown paths under `/en/` and `/tr/`, already get the server-rendered global 404 (`src/app/global-not-found.tsx`); `/admin` and `/api` answer their own 404s (Payload). Removed fixed paths answer 410: `src/proxy.ts` checks `isGone()` in `src/lib/gone.ts` and shows the removed-page with status 410. Pages that show a database record (institutions, subfield hubs, jobs; events from M8) are resolved in the proxy before rendering (`src/lib/detail-routes.ts`, with the database lookup in `src/lib/detail-lookup.ts`): unknown record, draft or job in review → 404, outdated or missing slug → 308, retired subfield, withdrawn job, job closed 30 days ago or job retired 12 months after that (only its address and ID kept in `retired-listings`, D34) → 410 with the same removed-page (`listingState()` in `src/lib/jobs/deadline.ts`). Add each new detail route there, and give its page `export const dynamic = 'force-dynamic'` (the build has no database).
- Robots rules live in `src/lib/indexing.ts`: a page's robots metadata and its sitemap entry (`src/lib/seo/sitemap-entries.ts`) come from the same function, so a page is in the sitemaps exactly when it is indexed. A new indexable page or record type gets its entry there too; `tests/e2e/seo.spec.ts` checks that every listed URL answers 200, without `noindex`, and names itself as canonical. The machine files (`/sitemap.xml`, `/sitemaps/*.xml`, `/en/jobs/feed.xml`) are route handlers that read the database at request time and answer 503 while it is unreachable; a name under `/sitemaps/` that no sitemap file can have gets the global 404 from the proxy.
- Access (PLAN §18.2): signed out, Payload's API gives nothing; public pages read through the local API with their own queries. Every collection and global states its rule for each operation with `signedIn` or `nobody` from `src/lib/access.ts`; a rule written as a function replaces Payload's default user check, so it checks `req.user` itself (field rules too). `tests/e2e/access.spec.ts` enumerates every collection and global from `src/payload-types.ts` and sends signed-out requests for every operation: a new collection needs an entry in its table, and a deliberately public read needs a reason there and a comment where its rule is set (`src/lib/access.test.ts` checks the rules as written). GraphQL is off.
- The Turkish editor guide, `docs/editor-guide-tr.md`, is what the admin shows at `/admin/help/` ("Yardım" at the end of the side menu, `src/admin/help.ts`, D45): keep it in step with the admin when the admin changes. It is read at run time, so it is kept in the Docker image (`.dockerignore`) and in the server build (`outputFileTracingIncludes` in `next.config.ts`).
- Payload is loaded from `node_modules`, not bundled (`serverExternalPackages` in `next.config.ts`): bundled, the production build copies it into each part of the server (instrumentation, proxy, routes, pages), and errors thrown by one copy fail `instanceof` in another, so the admin loses the per-field messages of refused saves. Keep it that way; `tests/e2e/admin-api.spec.ts` checks it.
- The map (PLAN §14, `src/components/map/`) loads MapLibre GL JS natively from `/map/maplibre-gl/<version>/`, which `src/scripts/vendor-maplibre.mjs` copies from `node_modules` before `next build` and `next dev`; never bundle it: its worker then comes from our origin (the CSP allows no `blob:` workers) and shares MapLibre's code with the page. Map code loads only where a map is shown (`engine.ts` on demand; on the jobs list through `LazyMapView`, since the list has 0.1 KB of its JavaScript budget left), within the map budget of `tests/e2e/budgets.spec.ts` (§17.3). The basemap's files are named by `/basemap/current.json` (`deploy/basemap/fetch-basemap.sh`; the tests serve `tests/fixtures/basemap` with `serveBasemap`, and check the map under the CSP of `deploy/Caddyfile` with `withSiteCsp`, `tests/e2e/map.ts`). Map colours come from the tokens at runtime. The map's data (`/api/map/institutions/`) resolves the jobs list's filters with the list's own code (`resolveJobFilters` in `src/lib/records.ts`), so map and list always count the same positions.
- Scheduled work lives in `src/jobs/`: the maintenance tasks (`src/jobs/maintenance/`, registered in `payload.config.ts` in the `maintenance` queue) are built with `maintenanceTask()`: idempotent, in bounded batches, one run at a time (a PostgreSQL lock), and logs and stored job errors with counts, IDs and error classes only (`src/lib/errors.ts`), never personal data. They run only where `PAYLOAD_JOBS_AUTORUN` is `true` (production). Retention periods are in `src/lib/retention/rules.ts` (D34). Code that deletes or clears personal data also clears the collection's saved versions (e.g. `_candidates_v`), since Payload keeps a copy of every save and has no route to delete one; deleting a record through the local API removes its versions. Automatic emails go through `deliver()` (`src/jobs/maintenance/email.ts`) only when `canSendEmail()` is true (SMTP_HOST set), are plain text from the `emails` messages, and set their sent-time only after the mail server accepted the message.
- Calendar days (a job's deadline day, "Last verified") are Payload date fields stored at noon UTC, so their UTC date is the day in every time zone; read them with `calendarDay()` and get instants with `deadlineEnd()` in `src/lib/jobs/deadline.ts` (a deadline day ends at midnight in `deadlineTz`, the institution's time zone unless the posting names another, or Anywhere on Earth when the zone is unknown; the institution's time zone is `Institution.timeZone`, from its coordinates, checked against its country (`timeZoneAt()` in `src/lib/jobs/time-zone-at.ts`, server-side only), which a new job takes when it is created without one, D40), never with the server's or the browser's time zone. Show them with `formatDay()` and `deadlineView()` in `src/lib/jobs/format.ts`, and take "now" from `requestTime()` in `src/lib/records.ts`, read once per request so a page, its lists and its metadata agree.

## Commands

Fill these in as the project grows.

- `docker compose up -d db` — start local PostgreSQL (values from `.env`; copy `.env.example`)
- `pnpm migrate` — apply database migrations
- `pnpm dev` — run the app locally (site on `/`, admin on `/admin`)
- `pnpm lint`, `pnpm typecheck`, `pnpm test` — checks (`pnpm format` fixes formatting)
- `pnpm test:db` — tests against PostgreSQL (`*.db.test.ts`), which need a connection that may create databases (`TEST_DATABASE_URL`, locally the `DATABASE_URL` of `.env`): those under `src/` each make and drop their own scratch database and role; those under `tests/integration/` (the scheduled tasks) share one scratch database, created, migrated and dropped again, and, where Docker is available, a throwaway Mailpit container; CI runs them too
- `pnpm test:e2e` — Playwright + axe tests against a running app (`pnpm build && pnpm start`, with the ROR test data and `pnpm fake:jobs` loaded; start the app after loading them, since it keeps the home page's figures for 10 minutes); every new page template goes into `tests/e2e/pages.ts`. `BASE_URL` sets the app's address (default `http://localhost:3000`) and `PLAYWRIGHT_CHROMIUM_EXECUTABLE` a Chromium already installed; with `--reporter=html` the report holds the pseudo-locale screenshots, and `budgets.spec.ts` prints each template's sizes
- `pnpm migrate:create <name>`, then `pnpm generate:types` — after changing a collection; commit the migration and types with it
- `pnpm migrate:status` — list the migrations and whether each has run
- `pnpm generate:importmap` — after adding or moving a custom admin component (such as the review dashboard); commit `src/app/(payload)/admin/importMap.js` with it
- `pnpm ror:import tests/fixtures/ror/v2.13-2026-09-22-ror-data-sample.zip` — load 20 test institutions (21 ROR records, one withdrawn and skipped; the e2e tests need them); without a file it downloads and imports the latest ROR release (about 15 minutes the first time)
- `pnpm fake:jobs` — replace the fake jobs at the test institutions (run it after `pnpm ror:import`): about 60 generated ones plus the fixed ones the e2e tests use (`src/scripts/fake-jobs-fixed.ts`: open, closing soon, rolling, closed recently, gone, withdrawn, draft (at an institution added by hand, the one an editor could delete), and a retired listing), then fake review-queue suggestions, candidates and reports in every state (`src/scripts/fake-queue-data.ts`; it also removes those the e2e tests sent). It refuses to run where `PAYLOAD_JOBS_AUTORUN` is `true` (production)
- `pnpm jobs:run [task …]` — run the scheduled maintenance tasks once (the hourly expiry, the form-limit and retention purges, the job places, the automatic emails; `src/jobs/maintenance/`), all of them or those named; the same tasks the production server runs on its schedule
- `pnpm tr:review` — regenerate `docs/tr-strings-review.md`, the table of every Turkish interface string for the native speaker's review (D40), after changing `messages/*.json`; a unit test fails when the file is out of date or a new key has no "where it appears" in `src/scripts/tr-strings-review-areas.ts`
- `docker compose --profile mail up -d mailpit` — local mail server for testing emails: set `SMTP_HOST=127.0.0.1` and `SMTP_PORT=1025` in `.env` (see `.env.example`) and read the messages at http://127.0.0.1:8025; nothing leaves the computer. Stop it with `docker compose --profile mail rm --stop --force mailpit`
- `E2E_EDITOR_PASSWORD=… pnpm e2e:editor` — add (or reset) the test editor `e2e-editor@example.org` that the admin API and access end-to-end tests use (one sign-in per run, `tests/e2e/editor.ts`: parallel sign-ins as one user drop each other's session); pass the same `E2E_EDITOR_PASSWORD` to `pnpm test:e2e` (without it the admin API test is skipped locally and the access test uses small IDs; CI always has it). It refuses to run where `PAYLOAD_JOBS_AUTORUN` is `true` (production)
- `gh workflow run deploy.yml --ref main -f tag=sha-1234567` (or GitHub → Actions → Deploy) — deploy by hand, only when the operator asks (a rollback, say): `main` or `sha-` plus 7 characters of a commit; merges to `main` deploy by themselves until M2, release tags `v…` from M2 on (D43); a new image that does not become healthy is rolled back by itself (`deploy/README.md`, "How deploys work")
- `sudo /opt/gliagora/basemap/fetch-basemap.sh [YYYYMMDD | --rollback]` (on the server, only when the operator asks) — the map's basemap, about twice a year (`deploy/README.md` step 8); `tools/basemap/make-fixture.sh` rebuilds the tests' small basemap
- `ssh gliagora@45.144.214.78` — the production server (only when the operator asks); `cd /opt/gliagora && docker compose -f compose.prod.yml ps` shows the stack, and `deploy/README.md` has the backup, restore and rollback commands
